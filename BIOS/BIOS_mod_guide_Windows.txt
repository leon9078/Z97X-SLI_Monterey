Entire BIOS mod guide!

Complete list of modifications:
1) Update the default 88:88:88:88:87:88 GbE MAC address to my specific one (74:D4:35:E6:42:2C)
2) Update Intel ME from 9.1.25.1005 to 9.1.40.1000
3) Update the module after "MERecoveryDxe" to include the updated first 512 KiB of SPI
4) Update with UBU tool:
   - Intel GOP driver + OPROM
   - Intel LAN driver + OPROM
   - Intel CPU microcodes
5) Update Setup, AMITSE and NVRAM modules:
   - enable hidden BIOS setting "ACPI Debug"
   - increase hidden BIOS setting "Setup Prompt Timeout" value from default 1 to 5
6) Delete 2 Microcode GUID ffs (one of them is a fake one that contains only FF, and the other one is the exact clone of another module)
7) Delete 2 "Padding file" sections, by adjusting Attributes
8) Replace bugged AMI "FileSystem" driver with "Fat" (EnhancedFatDxe from FatPkg audk [fork of tianocore EDK II project focused on security])
   Add my specific version which removes FAT32 FsVersion check during driver initialization
9) Update "CORE_DXE" module to include "OpenCore" and "Gentoo" for automatic detection of specific bootloader paths

The idea of creating a custom BIOS file started because I was fed up with my specific Intel LAN MAC address (74:D4:35:E6:42:2C) being "reset" to the default (88:88:88:88:87:88)
every time I flashed the original OEM BIOS file using fpt (Intel Flash Programming Tool) without any additional parameter

The following command will flash the entire BIOS image including the GbE region with the wrong (default) MAC address:
> fpt -f Z97XSLI.10b

To avoid replacing my specific MAC address, I need to specify an additional parameter, "-savemac"

> fpt -savemac -f Z97XSLI.10b

This will prevent the MAC address from being overwritten

- Attributes: 00h
- Data checksum: AAh, valid



We have to find the section type and ffs type, so we can use that info later.

File Types: https://github.com/LongSoft/UEFITool/blob/A73/common/ffs.cpp#L284-L299

Now go down, check the "Subtype" value of the "Section" type, it says "Compressed"
Double check on the link above the result: EFI_SECTION_COMPRESSION
And so on, till the end of the module.



In (https://github.com/LongSoft/UEFITool/blob/A73/common/ffs.h#L328-L335)
"FFS_ATTRIB_CHECKSUM" is bit 6h (0x40)

In (https://uefi.org/specs/PI/1.9/V3_Code_Definitions.html#efi-ffs-file-header)
"If the FFS_ATTRIB_CHECKSUM bit of the Attributes field is cleared to zero, the IntegrityCheck.Checksum.File field must be initialized with a value of 0xAA."
Our "Attributes" does not have the Data Checksum bit set (0x40), indeed it has a value of 0xAA.

Now, I wanted to fix this ACPI issue I have in DSDT:

    External (MDBG, IntObj)

    Method (ADBG, 1, Serialized)
    {
        If (CondRefOf (MDBG))
        {
            Return (MDBG) /* External reference */
            Arg0
        }

        Return (Zero)
    }

MDBG is recognized as a "IntObj" which is wrong. It is a "MethodObj", since it contains Arg0 in the Return!
This happens because there is a missing ACPI table which is not loaded at runtime
So I tried to search inside UEFITool if there is an ACPI table which has this Method and I found it!

{ 05 A6 1C 0F 1D 0F 18 03 ... }
Label ID is the 2 bytes at offset 2-3h: 1C 0F
Help Label ID is the 2 bytes at offset 4-5h: 1D 0F

As we can notice, the first byte of "Help Label ID" is ALWAYS one value more than the "Label ID" one. 1D > 1C

Now we need to create our Find sequence in Hextor in order to find our 2 HEX bytes to flip from 00 (Disabled) to 01 (Enabled)

So, we start with the QuestionId value in little endian (backwards). The initial value is 0x318. We want to pad the value with a leading zero to reach even digits, so 0x0318
Now we separate the digits, 0x03 0x18. Now Little Endian became 0x18 0x03

So, the initial (QuestionId) sequence to Find is: \x18\x03

Now there are next 18 HEX bytes to match, so we use "Extended syntax" feature in Hextor. The syntax will be: {byte::18}
Then there is "Help Label ID" value: \x1D\x0F
Then 26 HEX bytes to match, syntax in Hextor: {byte::26}
Then "Label ID" value: \x1C\x0F
Lastly, 2 HEX bytes to match. We can short the syntax: ??

So, the final sequence in Hextor is: \x18\x03{byte::18}\x1D\x0F{byte::26}\x1C\x0F??

######## BEGIN ########

Background: AMI APTIO IV platforms include "FileSystem" driver which is their FAT file system implementation. Unfortunately, this UEFI driver contain bugs that corrupt the file system on write attempts...
Use the improved EnhancedFatDxe from acidanthera audk (which is a fork of tianocore EDK II project focused on security)!

More over, I want to add my specific version of the driver, which basically remove the FAT32 FsVersion check during driver initialization. Why I did this?
Well, Microsoft Windows OS is an ASS! Whenever I have 2 separate hard disk drives in my PC attached and I boot into Windows, it will ALWAYS create the infamous "System Volume Information" to any file system
the OS automatically recognize, such as FAT (all variants), NTFS etc...
UEFI spec "encompasses the use of FAT32 for a system partition, and FAT12 or FAT16 for removable media."
This is the default file system for the EFI System Partition, and it's done for comatibility across different operating systems.

So back to the previous example, if I have 2 different HDD attached and I boot Windows, it will add "System Volume Information" to the ESP of the other disk as well, which could have another OS (such as Linux or macOS)
No matter if the ESP of that disk has GPT attributes set, such as:
- bit 60 (Read-only)
- bit 62 (Hidden)
- bit 63 (No drive letter, do not automount)

...it will ALWAYS mount that partition and create that infamous folder...

The ONLY thing that prevent Windows from mounting a FAT partition is by setting FsVersion to a value other than "00 00". Ref: https://raw.githubusercontent.com/ryansturmer/thinfat32/master/fatgen103.pdf

This field is defined at offset 42 of BPB (BIOS Parameter Block), which is found at sector 0 of the partition.

Also, "This field is only defined for FAT32 media and does not exist on FAT12 and FAT16 media. High byte is major revision number. Low byte is minor revision number.
This is the version number of the FAT32 volume. This supports the ability to extend the FAT32 media type in the future without worrying about old FAT32 drivers mounting the volume.
This document defines the version to 0:0. If this field is non - zero, back- level Windows versions will not mount the volume.
NOTE: Disk utilities should respect this field and not operate on volumes with a higher major or minor version number than that for which they were designed.
FAT32 file system drivers must check this field and not mount the volume if it does not contain a version number that was defined at the time the driver was written."

Indeed, when using "diskpart" to e.g. assign a drive letter to a FAT partition, the "Fs" value changes from "FAT32" to "RAW", making it unrecognizable by the entire OS!
To check this, open an elevated command prompt:

> diskpart
DISKPART> lis dis
DISKPART> sel dis=X
DISKPART> lis par
DISKPART> sel par=1 // Usually the ESP is the first partition of the disk
DISKPART> det par

Check the "Fs" value, should be "FAT32" if FsVersion equals 0 (00 00), otherwise "RAW"

DISKPART> exit
> exit



On the other hand macOS, by default, will NOT mount any GPT partition with the EFI Partition type GUID (C12A7328-F81F-11D2-BA4B-00A0C93EC93B)
But if the user try to mount the ESP from macOS environment, the OS will automatically add at least one of those trashy files/folders:

Linux, instead, will happily mount any FAT32 which has a FsVersion different then 0!
    .Trash-1000 folder is created by a DE in Linux IF the user move the file to Trash. It could be prevented IF the user directly delete the file/folder



So, to come around all of this shit, we embed our version of EnhancedFatDxe driver in our firmware.
My version removes the FAT32 FsVersion check during driver initialization!

Reference here:
- C header file: https://github.com/acidanthera/audk/blob/bc664d1830c9446cb1d33b10a41e6b3d207997f1/FatPkg/EnhancedFatDxe/FatFileSystem.h#L120
- C source code: https://github.com/acidanthera/audk/blob/2f3189030892cbda40c3f1d47d7ec5f1f40a0709/FatPkg/EnhancedFatDxe/Init.c#L323



WARNING: we all know we can choose between many different bootloaders to boot our favourite OS, but while some of them inherit file systems from firmware, some of them have their own implementations.
Not exaustive list of bootloaders (with file system details) here: https://wiki.archlinux.org/title/Arch_boot_process#Feature_comparison

I will give you 2 examples:
1) OpenCore (what I will use with Gentoo!)
    This bootloader inherit file systems from the firmware (so in my case our custom version of EnhancedFatDxe)
    But it can also load additional file systems by adding UEFI drivers into the Drivers\ folder and enabling in the config.plist

2) GRUB2 (the default choise of the majority of Linux distros, except Arch Linux)
    It has their own implementation of multiple file system drivers

So, when using GRUB in UEFI mode, this is the early boot chain:
1) UEFI firmware will load the custom embedded EnhancedFatDxe driver
2) When loading GRUB bootloader it will actually load their FAT file system implementation

This second point is crucial, because IF we change the FAT32 FsVersion of an ESP to a value different than 0 (00 00),
our custom EnhancedFatDxe UEFI driver will load fine, but then GRUB will FAIL to load the ESP and jump into rescue mode. Why?
Because they also have the FAT32 FsVersion check in their own implementation

Reference here:
- C header file: https://gitlab.freedesktop.org/gnu-grub/grub/-/blob/master/include/grub/fat.h#L55
- C source code: https://gitlab.freedesktop.org/gnu-grub/grub/-/blob/master/grub-core/fs/fat.c#L370



So, to come around this issue with GRUB, we have 3 solutions:
1) Avoid setting FAT32 FsVersion at all
    With this solution we can have issues when macOS/Windows try to mount the ESP by creating custom file/folders inside the file system...
2) Recompile our custom version of GRUB which removes the FAT32 FsVersion check, much like we did with our previous EnhancedFatDxe driver
    This solution is not advised, because the majority of Linux distros already include their standard "grub" version within their package manager
3) Use OpenCore bootloader with Mike Beaton's OpenLinuxBoot driver!
    This appear to be the best solution!!!

For the modified "Gentoo" entry I'm defining "GENTOO.EFI" instead of the traditional "grubx64.efi". This is because I want to use OpenCore bootloader instead of the traditional GRUB 2 bootloader when using Gentoo!
More over, to make a clear distinction for the end user between booting macOS (through OpenCore) and booting Gentoo (also through OpenCore),
we rename (this time for the file system, and not for the UEFI bootloader path) the "EFI\OC" directory to "EFI\GENTOO" and change "OpenCore.efi" to "Gentoo.efi"

The choise of "Gentoo.efi" comes from a variety of different naming options. The filename "*.efi" without extension ".efi" must be between 4 and 7 characters inclusive, so possible candidates are:

- Linux ------> maybe too generic...
- Gentoo
- BOOTx64 ----> could be confused with the existing \EFI\BOOT\BOOTX64.EFI already defined...
- bzImage ----> should be typically used only for EFI stub (pure UEFI boot, without an additional bootloader)
- vmlinuz ----> should be typically used only for EFI stub (pure UEFI boot, without an additional bootloader)
- OpenCore ---> already have OpenCore.efi defined...

So, at the end I choose "Gentoo.efi" as the final candidate, becuase it makes more sense!

Why I choose OpenCore with OpenLinuxBoot instead of pure EFI stub?

Well I found that booting a Linux kernel using EFI stub (using just the UEFI bootloader, skipping a secondary bootloader), has 4 main disadvantages:
1) Linux kernel (and initramfs/initrd) reside on a FAT file system. This is a big security issue, because every UEFI PC has an embedded FAT file system UEFI driver in their firmware.
    This driver has read-write capability, so anyone could theoretically access the ESP of the disk and replace or delete the content from within the UEFI Shell, making it impossible to boot Linux!
2) As we already know, the ESP has a FAT file system, and this file system is not robust at all.
    It's really old and relatively simple to understand by other OS. Does not support journaling, neither UNIX permissions...
3) The user have to constantly deal with the ESP every time there's a kernel upgrade. So every time the package manager install a new kernel/initramfs, the latter is copied to the ESP either
    automatically:
        through some scripts, in the case of Gentoo using sys-kernel/installkernel with the "efistub" USE flag
    manually:
        the user have to manually mount ESP and copy the updated files into it
4) The user MUST always create a new Boot#### NVRAM entry in their UEFI firmware in order to boot the OS, and to do so it has 2 options:
    From UEFI Shell:
        Shell> map
        Shell> ls -a FSX:\ // List the content of the ESP, where X is the number of the recognized FAT partition
        Shell> ls -a FSX:\EFI\
        Shell> ls -a FSX:\EFI\[...]
        Shell> bcfg boot dump
        Shell> bcfg boot add 0 FSX:\bzImage-6.12.12 // The number 0 means add it as the top most UEFI entry
                                                    // 6.12.12 is an example of a specific Linux kernel version
                                                    // The name bzImage came from the original name of ./arch/x86/boot/bzImage
                                                    // Another popular name choise is vmlinuz
                                                    // The .efi extension at the end is optional
        Shell> bcfg boot -opt 0 "initrd=\initramfs-6.12.12.img" // If using a Linux kernel that needs an initramfs/initrd, it must have this kernel argument

    From a Linux OS (booted in UEFI mode) with efivarfs rw:
        # efibootmgr
        # efibootmgr --create --disk /dev/sdX --part Y --label "Gentoo" --loader /bzImage --unicode 'initrd=\initramfs-6.12.12.img'
            // /dev/sdX for USB/SATA disks, for NVMe/M.2 disks use /dev/nvme0nX

For the last point, creating every time a UEFI entry is not ideal at all, since it have to deal with NVRAM every time...
We could have an already defined UEFI DevPath in our custom CORE_DXE UEFI module, such as \EFI\GENTOO\BZIMAGE.EFI, but this is supposed to be an initramfs-less solution.
For Linux kernel with an external initramfs/initrd we NEED to specify the "initrd=" option, so embedding a custom Linux EFI stub DevPath in CORE_DXE can'not be an option!

Now, sum the number of characters to Find/Replace: 12 + 28 + 20 + 24 + 8 + 24 + 20 + 20 + 24 + 36 = 216
We need to replace 216 UCS-2 bytes (432 bytes)

Now we have to create our Hextor find sequence:

The initial find sequence begins with "opensuse". Next we need to add x4 "\x00" to the end!
This will also be useful later because we want to add a fixed number of "\x00" at the end of each string as we noted above.
Our find sequence is now: "opensuse{u16:0x00:4}"
Now we have to add the remaining number of UCS-2 bytes to sequence until we reach number 216
"opensuse" is 8 characters.
"\x00" is 4 characters.
Remaining bytes will be: 216 - (8 + 4) = 204

Our new sequence will be: "opensuse{u16:0x00:4}{u16::204}"



Now let's move to the Replace sequence

We are changing the case of the openSUSE Description from "opensuse" to "OpenSUSE". Then DevPath uppercase.
Next, we have "OpenCore" with x12 extra NUL characters. Then DevPath uppercase.
This time, in the replace sequence we can not add "{u16:0x00}" as it will be recognized as a string to replace.

One way is using this notation: "\x00", but later when we have to deal with multiple NUL characters we would type: "\x00\x00\x00\x00"

Another more efficient way is to use a feature in Hextor called "Indexed subexpressions".
Basically, find sequence becomes: "opensuse({u16:0x00:4}){u16::204}"

But if we do this way, our value inside round brackets would be \x00\x00\x00\x00, basically x4 \x00 value. This will be a problem if our replace value will need less than 4 NUL characters after each string...
So we want to change this by only selecting 1 NUL character inside the round bracket and then add 3 more bytes to the curly brackets.
So the FINAL find sequence will be: "opensuse({u16:0x00}){u16::207}"

while replace sequence now becomes: "OpenSUSE$1$1$1$1"

"$1" in this case means: "{u16:0x00}"

Now that we understand this pattern, it's easy to continue till the end of the Replace sequence:
